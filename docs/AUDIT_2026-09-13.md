# I-Crash — independent project audit

Date: 2026-09-13
Auditor: Claude (Cowork session), working from the connected `ICrash` folder
Scope: the whole repository as it stands on branch `DEV-Martim` @ `8041455`

This is an *audit*, not a restatement of `docs/IMPLEMENTATION_STATUS.md`. Every
number below was measured from the source tree. Where a claim could not be
independently re-verified in this session, it is labelled as such.

---

## 1. Verdict in one paragraph

The V2 rebuild is substantially complete as an engineering artefact and is
unusually well documented for a student project. 47 commits over two days
(9–10 Sep 2026) took the app from a 2022-era Django/HTTP prototype to a layered
Flutter + Firebase application with ~10k lines of new source, 132 automated
tests, 27 Firestore Rules tests, role-based security rules, GS1/QR scanning and
full PT/EN localization. What is *not* complete is everything around the code:
the work has never been merged to `main`, there is no CI, the entire Firestore
data layer has no automated coverage, the root `README.md` still describes the
dead Django stack, and five heavy native dependencies are kept alive purely by
abandoned prototype files. None of that is hard to fix; all of it is the kind
of thing that quietly costs marks in an evaluation and hours in a handover.

**Maturity**: strong prototype / pre-release. Not distributable (debug signing).

## 3. Findings

Ordered by how much they would cost to ignore.

### F1 — `main` has never received any of the work · **High (process)**

`main` and `origin/main` are still at `8e0e619`, the pre-modernization baseline.
All 47 commits exist only on `DEV-Pedro` and `DEV-Martim` (both at `8041455`,
both pushed). There is no merge, no pull request, no tag, no release baseline.

Consequences: anyone cloning the repo and checking out the default branch gets
the 2022 Django prototype, not the product. There is also no reviewed
integration point — the two DEV branches are byte-identical, so `DEV-Martim`
currently carries no independent contribution of yours.

**Do**: open a PR `DEV-Pedro → main`, review it, merge, and tag (`v2.0.0-rc1`).

### F2 — The Firestore data layer has zero automated coverage · **High (correctness)**

`lib/src/data/firebase/` is 1 139 lines across 12 files — the actual Firestore
reads, writes, batches and stream mappings. No test file references any
`Firestore*Repository` or `FirebaseAuthRepository`. Every widget test runs
against hand-written fakes in `test/fakes/fake_repositories.dart`, and the
Rules tests exercise `firestore.rules` directly via the emulator, bypassing the
Dart code entirely.

So the layer where a wrong field name, a wrong collection path or a mis-ordered
batch would actually live is validated only by manual Android walkthroughs
performed by one person on one emulator. Those walkthroughs are thorough (see
`TEST_STATUS.md`) but they are not repeatable and they do not run on a change.

**Do**: add `integration_test/` (or `flutter_test` + `fake_cloud_firestore`)
covering at minimum `createAssignment` uniqueness, `reconcileAfterAudit`,
`recordCorrection`, and the `memberships`/`memberIndex` paired write.

### F3 — Dead code keeps five native dependencies in the build · **Medium**

Measured dependency usage across `lib/`:

| Package | Used only by | Status |
|---|---|---|
| `google_mlkit_text_recognition` | `lib/teste/teste.dart`, `teste_v3_text_reader.dart` | dead weight |
| `google_mlkit_barcode_scanning` | `lib/teste/teste_v2.dart` | dead weight |
| `zxing_lib` | `lib/teste/teste_v1.dart` | dead weight |
| `camera` | `lib/teste/*` (4 files) | dead weight |
| `image` | `lib/teste/teste_v1.dart` | dead weight |
| `http` | `lib/request_handler/request_handler.dart` (Django client) | dead weight |
| `cupertino_icons` | nothing | unused |

`lib/teste/` is four scanning prototypes superseded by
`lib/src/services/gs1_*`. Keeping them costs real APK size, pulls two ML Kit
native SDKs, and — per `MODERNIZATION_2026.md` — is what forces the **iOS
minimum to 15.5**. `lib/teste/teste.dart` is still imported by `home_menu.dart`,
so it is not trivially deletable: the legacy screens must go first.

**Do**: delete `lib/teste/`, `lib/request_handler/`, `lib/grids/`,
`lib/registration/`, `lib/qr_code_reader/`, `lib/updates/`, `lib/home_menu.dart`
and the dashboard's "legacy app" entry point, then drop the seven packages
above. The history is in git; the academic record is in `RELATORIO/`. Do this
*after* F1, as its own commit, so it is reviewable and revertible.

### F4 — The root `README.md` is three years stale · **Medium (presentation)**

`README.md` still documents the LEIC deliverable: PostgreSQL install steps,
`python manage.py migrate`, editing `settings.py` line 83, copying a `lib`
folder into a fresh Flutter project. It mentions neither Firebase, nor `docs/`,
nor the emulator workflow, nor how to actually run the current app. It is the
first thing a supervisor, an evaluator or a recruiter reads.

**Do**: rewrite it — what I-Crash is, the current stack, how to run the
emulator + app, where `docs/` starts, and a one-line pointer to the preserved
academic material.

### F5 — No CI · **Medium**

No `.github/workflows`. `flutter analyze`, `flutter test` and `npm test` are
run by hand on one Windows machine. Every quality claim in `docs/` is therefore
a point-in-time assertion that nothing re-checks.

**Do**: one GitHub Actions workflow on push/PR — `flutter analyze`,
`flutter test`, and the Rules suite against the emulator. It is roughly 40 lines
and it makes every future "132/132 passing" claim self-evidencing.

### F6 — Release blockers (all human-gated, correctly documented) · **Medium**

Confirmed, and `RELEASE_CHECKLIST.md` is honest about each:

- Android `release` signs with the debug key — nothing built today is
  distributable or Play-uploadable.
- iOS/macOS: no signing, no device testing, nothing verified (Windows-only dev
  environment).
- Web and Windows: builds pass and the Windows `.exe` launches, but **no UI
  click-through has ever been done** on either. Only Android has live
  validation.
- Store assets (icon set, screenshots, privacy policy) not started.

The Web walkthrough is the one item here that needs no account, no Mac and no
secret — it is the cheapest remaining validation win.

### F7 — Functional limitation: cross-cart alerts are manager+ only · **Medium (product)**

Institution-wide expiry/low-stock alerts (spec §49) are visible only to
manager/admin roles. This is forced by a Firestore Rules constraint — a
collection-group `list` rule may only reference fields the query itself filters
on — and is well documented in `FIREBASE_MODEL.md`. It is nonetheless a
behaviour a nurse responsible for a cart will notice and ask about. Worth a
deliberate decision (different query shape, or a maintained denormalized alert
document) rather than leaving it as an implementation consequence.

### F8 — Slot identity is positional · **Medium (data integrity)**

Slot ids are `r{row}c{column}` of the top-left cell, unique only within a
drawer. Merging or splitting an assigned drawer changes which ids exist and can
strand a `CartProductAssignment`. The latest work added detection and a
manager-facing reassign/delete UI — that handles the symptom. The root cause
(ids not stable across edits, and theoretically collidable between drawers) is
still open and needs a migration story. Flagged in the handoff; repeating it
here because it is the one open item that can corrupt real inventory data
rather than merely inconvenience a user.

### F9 — 17 clinical/business decisions still unanswered · **Medium (scope risk)**

`OPEN_DECISIONS.md` lists 17 questions — audit frequency, minimum stock levels,
whether GS1 scanning becomes mandatory, who may correct history, expiry warning
windows, and so on. These were correctly not invented by an assistant, but they
are not cosmetic: several of them determine whether the implemented conservative
lot-expiry logic is the *right* logic. Until a clinical stakeholder answers
them, "complete" means "complete against an assumed model".

**Do**: get these in front of a real clinical contact (or your supervisor, as
proxy) before any further feature work. Answers may invalidate implemented
behaviour, and that is far cheaper to learn now.

### F10 — Single-author, single-machine concentration · **Low–Medium (project)**

All 47 commits are authored by `Pedro15092001`, from one Windows environment,
in a 2-day window; nothing has been committed since 10 Sep. `docs/` encodes
absolute paths from that machine (`C:\Users\Pedro Jorge\...`) as the canonical
environment. `DEV-Martim` contains no commits of its own.

For a two-person project this is a bus-factor and an attribution issue. If the
evaluation looks at contribution history, it currently shows one contributor.

### F11 — Firebase client config is committed (expected, but understand why) · **Informational**

`google-services.json` and `lib/firebase_options.dart` (5 `apiKey` entries) are
tracked. This is normal and correct for Firebase client apps — those keys are
public identifiers, not secrets. It does mean **all** access control rests on
`firestore.rules` and Auth. `.gitignore` correctly excludes `.env`, `*.key`,
`*.pem` and `*service-account*.json`; no private credential is in the tree.
Worth noting only because App Check is not enabled (Spark plan, no billing), so
there is no attestation layer beneath the Rules.

## 4. What is genuinely done well

Stated plainly, because an audit that only lists problems misrepresents this
repository:

- **The layering is real.** `domain/` has no Firebase import; repositories are
  interfaces; `InventoryRules` is pure and directly unit-tested, including the
  two literal spec scenarios. This is the part most student projects skip.
- **Security was designed, not bolted on.** 27 Rules tests covering role gates,
  per-cart `responsibleUsers` access, field-level write scoping, and immutable
  audit/usage events. The deny-all → scoped-rules progression is the right one.
- **The documentation is exceptional.** `AI_HANDOFF.md`, `TEST_STATUS.md` and
  `IMPLEMENTATION_STATUS.md` record not just what was built but what broke, why,
  and what was deliberately *not* done. The `MainActivity` package bug, the
  collection-group Rules failure mode, the emulator `clearFirestore()` foot-gun —
  all captured. That is genuine institutional memory.
- **Trade-offs are stated, not hidden.** Fixed-Portuguese exports, the
  `WriteBatch`-not-transaction reconciliation, the AI 10 truncation limit — each
  is documented with its reasoning and, where relevant, a test pinning the
  behaviour.
- **The academic record was preserved.** Planning, analysis, design and the
  final PDF are untouched; the modernization sits alongside rather than over it.

## 5. Recommended order of work

1. **Merge to `main`** and tag a baseline (F1). Nothing else should land first.
2. **Rewrite `README.md`** (F4) — highest visibility per hour spent.
3. **Add CI** (F5) — makes every later change self-verifying.
4. **Delete the legacy tree and its seven dependencies** (F3), as one reviewable
   commit, immediately after CI exists to catch fallout.
5. **Put the 17 open questions to a clinical stakeholder** (F9) — long lead time,
   start it in parallel with the above.
6. **Web UI click-through** (F6) — cheapest remaining platform validation.
7. **Data-layer tests** (F2), starting with the inventory write paths.
8. **Decide on slot identity** (F8) and on cross-cart alert visibility (F7).
9. Release signing and store assets (F6) — last, and only once someone owns the
   developer accounts.

  inspected; the repository copies were.
