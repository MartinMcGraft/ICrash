## 2. Users (D16, D18)

### 2.1 The three types

| Type | Who | Scope | Uses | Code role today → target |
|---|---|---|---|---|
| **Super** | The **I-Crash team's** IT staff | Fixes app problems, ships updates, helps the institution's IT. Reaches **several institutions, one at a time, only on request** (D18) | Dashboard, tablet and phone (every screen type) | `platformSuperAdmin` (keep) |
| **Admin** | The **institution's** IT staff | Everything in **one** institution: all carts, users, catalogue, templates, settings, devices. No access to other institutions | Dashboard; tablet or phone to test changes | `institutionAdmin` (keep) |
| **Manager** | A **health professional** | Full access to the **carts they are registered to** (the cart's responsible users, `responsibleUsers` / CrashCartUser), nothing else | Tablet or phone; may use the Dashboard | `manager`, narrowed to registered carts |
| ~~User~~ | — | **Dropped.** Existing `user` memberships become `manager` | — | `user` (remove) |

Notes:
- "Full access" for a Manager means every cart action (consume, replenish, correct, reconcile,
  monthly check, sign, change state) on their carts. Whether a Manager may also **edit the
  structure** (drawers, grid, catalogue, templates) stays with R7: structure editing is Dashboard
  work and, by default, **Admin only**; the B7 toggles can grant it.
- This replaces the 28 Oct reading of P14 ("the Engineer Admin is the institution's IT"): that role
  is now **Admin**; **Super** is the I-Crash team.
- One institution per user is unchanged. The institution picker exists **only for Super** (§3.3).

### 2.2 Support access (D18): privacy rules

Super is outside the institution, so its access is the exception to "nothing leaves the
institution". The prototype must make it visible and limited:

1. **Off by default.** An Admin opens it in the Dashboard ("Acesso do suporte"): reason (free
   text), duration (e.g. 4 h, 24 h, 7 days; maximum to confirm), and can close it at any time.
2. **Super sees only institutions with an open grant.** No grant → the institution doesn't appear
   in Super's picker and the Firestore rules refuse its data.
3. **Every Super session is logged** (who, when, which institution, grant used) in a log the Admin
   can read and Super can't edit or delete.
4. **Banner while inside:** "Acesso do suporte · {instituição} · termina às {hora}".
5. **No patient data** exists anywhere (business rule 9), so the data reached is stock, users'
   names/e-mails and history. Super never sees PINs or passwords (only hashes exist).
6. In the local-server version the grant is a VPN/remote-session window opened by the hospital;
   the log stays on the hospital's server. Database: open point **DB13**.

## 3. Signing in and device setup (D17)

### 3.1 Why the PIN needs a first sign-in today (answer to "are these Firebase rules we defined?")

It isn't one of our Firestore rules. **Firebase Auth** requires every read and write to come from
a signed-in Firebase account, and a 4-digit PIN isn't a Firebase credential. Turning a PIN into a
sign-in needs server code (Cloud Functions), which the Spark plan doesn't allow. That's why A2/A3
only work after the user signed in with e-mail + password once **on that device**: the device
keeps that user's Firebase session and checks the PIN locally.

### 3.2 The new flow

1. **Delivery:** I-Crash hands over the tablet with the app installed.
2. **Setup (Super and/or Admin), once per device:** on the tablet, "Configurar dispositivo": an
   Admin (or Super with an open grant) signs in with their own password, names the device
   ("Tablet Carro 3 · UCI") and optionally binds it to carts. The app creates a **device account**
   for the institution (a Firebase user with a `device` membership, created the way B7 creates
   users) and stores its credentials on the device. The Admin's own session ends.
3. **Daily use:** A1 on a registered device shows **"Desbloquear com PIN"** (user number or e-mail
   + PIN) and **"Entrar no carro"** (scan the cart's QR, then PIN). No password.
4. **Personal devices** (an Admin's laptop, a Manager's phone) keep e-mail + password sign-in.
5. Admin sees and **revokes** devices in the Dashboard (new list under B7 or B3). A revoked device
   goes back to step 2.

**Firestore rules change needed** (emulator first, deploy only with Martim's OK):
- a `device` membership may read the PIN hashes (`memberships/*/private/credentials`) of its own
  institution, and nothing it couldn't read for the acting user;
- writes made on a device carry the **acting member's uid** (`actorUid`), which must be an active
  member of that institution (and, for a Manager, registered to the cart);
- **Known limit (prototype):** the rules can't prove that the PIN was typed by that member, and the
  device can read every hash of its institution (a 4-digit PIN is brute-forceable from a hash).
  Acceptable for the prototype; the local server checks the PIN itself.

## 4. Phone vs tablet (D21)

### 4.1 What differs today, and why

On a phone (height < 500 px) several screens **hide** items to fit 390 px of height. That was a
space decision, not a permission one, and it removed actions people need:

| Screen | Hidden on the phone today | Why it was hidden | Decision |
|---|---|---|---|
| A5 Cart, header | "Responsável no turno" | Keep the header to one line | Shown in the cart menu on phones (phase 2) |
| A5 Cart, drawers | "Gavetas" section title; the grid line ("5 × 6 · 30 posições") | Rows are 60 px instead of 76, and the state line needs the room (phase 1) | OK as is (information, not an action) |
| A5 Cart menu | **Alterar estado**, **Relatórios do carro**, the menu title, the emergency hint | Menu fits without scrolling | **Show the actions** (menu may scroll vertically) — RV-10 |
| A5 Cart menu | "Mostrar código QR" shortened to "QR" | Width | Removed from the App (RV-21, phase 2) |
| A6 Drawer panel | Big quantity number (shown inline instead), **lot**, **Trocar produto / Limpar posição / Corrigir / Reconciliar** row | Panel fits 390 px | **Show the actions**; the panel may scroll vertically, or the secondary actions go into a "Mais ações" menu — RV-11 |
| A6 Drawer panel | Long expiry date ("12/03/2027 (134 dias)") → short ("12/03") | Width | Keep the short form, add the days |
| A8 Monthly check | Help text | Height | Goes with the A8 rewrite |
| A9 Report | Signing help text | Height | OK |
| Shell | Rail 72 px instead of 96; smaller buttons (`IcButtonSize.m`) | Space | OK |

**Rule from now on (D21):** a phone may change *how* things are shown (shorter labels, smaller
buttons, vertical scrolling, a "Mais ações" menu), never *what* the user can do. Any
`if (!compact)` around an action is a bug.

safe-area insets**, and doesn't cover A5/A6/A8/A9 on a phone. Real devices are smaller:

| Device (landscape) | Logical size | Usable after safe areas |
|---|---|---|
| iPhone 16 | 852 × 393 | about 734 × 372 (notch side 59 px each side, home indicator 21 px) |
| iPad mini (6th gen) | 1133 × 744 | about 1133 × 724 |
| iPad Pro 13" | 1376 × 1032 | fine |

The layout test must add **iPhone 16 with insets** and **iPad mini** sizes and every A-screen.
**Done in phase 1:** the "real devices" group of `layout_fit_test.dart` renders A1, A4 (real
App shell), A5, A6, A8 and A9 inside the App shell frame with those insets, and also fails
when a button label (or, in A5, any text) is cut. It reproduced RV-5–RV-9; the rail also

## 6. Terminology (D19)

  catalogue CSV becomes "Consumível"; the import still accepts the old header).

  ClinicalConsumable.

  catalogue import (skips a "Consumível" or the old "Produto" header).
